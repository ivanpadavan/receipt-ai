### Дополним задачу: Server Updates (ReceiptFormInner)
Сейчас часть server update-сценариев покрыта только частично. Это отдельный пробел покрытия.
Ожидаемый рост `ReceiptFormInner.browser` для закрытия пробела: примерно `x1.5 - x2`.

Что не покрыто полностью и нужно добавить:
1. Realtime update во время активного редактирования (`editing/splitting` открыты): подтверждение, что локальный draft не теряется и UI-инварианты не ломаются.
2. Конкурирующие обновления с сервера (несколько апдейтов подряд): корректный итоговый state после серии событий.
3. Апдейт с сервера, который меняет доступность действий (например, `canProceed`, `max`, `remaining`) во время уже открытого экрана.
4. Внешние изменения участников/клеймов во время текущей сессии: консистентность `ParticipantsSheet`, `SplittingSheet`, summary-блоков.
5. Потеря/восстановление соединения (`sseDisconnected` / `sseReconnected`) в сочетании с уже открытыми экранами и последующим апдейтом.
6. Серверный rollback/коррекция после optimistic-изменения: UI корректно синхронизируется без “resurrect” и без визуального рассинхрона.
7. Скриншоты для ключевых server-update состояний: baseline на момент “до апдейта”, “после апдейта”, “после reconcile”.

Критерий готовности по этому блоку:
- server updates покрыты не точечно, а системно для основных режимов `validation/splitting/summary`;
- есть screenshot-baseline для критичных состояний после серверных изменений;
- нет flaky-поведения между `headless/headed` при повторных прогонах.

### Как делаем тесты (правила)
1. Формат каждого теста: `AAA` (Arrange -> Act -> Assert).
2. В `Arrange`:
   - создаём `userEvent.setup()`;
   - рендерим через общий `render`-хелпер;
   - подготавливаем фикстуры (receipt/participants) из отдельного файла.
3. В `Act`:
   - только действия пользователя (клики, ввод, клавиатура, открытие меню/диалогов);
   - без ассертов и без побочных проверок.
4. В `Assert`:
   - сначала смысловые проверки UI/состояния (`getByRole`, `getByText`, `queryBy...`);
   - затем screenshot-проверка (`expectCurrentScreenshot`) для визуального baseline.
5. Структура тестового кода:
   - большие фикстуры выносим в `*.fixtures.ts`;
   - повторяющиеся операции/поиск элементов выносим в `helpers`/утилиты;
   - в основном тесте оставляем только сценарии и assertions.
6. Моки:
   - мокируем только внешние зависимости (router, query state, api-client, auth, provider-обвязку);
   - бизнес-логику компонента не подменяем.
7. Правила screenshot-тестов:
   - единый viewport для браузерного набора;
   - осмысленные имена baseline-файлов (по состоянию экрана/сценария);
   - обновление baseline только осознанно (`-u`) после проверки диффов.
8. Детеминизм:
   - фиксированные тестовые данные;
   - запрет на рандом/время без стабилизации;
   - после каждого теста очищаем окружение (`cleanup`, reset env/mocks).
9. Именование тестов:
   - поведенческие названия в настоящем времени (`opens ...`, `keeps ...`, `transitions ...`);
   - один тест = один пользовательский сценарий.
10. Приоритет ассертов:
   - сначала продуктовые инварианты (что пользователь видит/может сделать),
   - затем детали реализации.
